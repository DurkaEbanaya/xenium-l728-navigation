# L728: SOS → блокировка/разблокировка и экран, v0.3.0

Дата: 2026-10-12. Исследование после проверенного релиза v0.2.0.
Цель — одна физическая SOS-кнопка для переключения блокировки; потеря
штатного SOS допускается владельцем. Результаты ниже получены офлайн из
совпадающих резервных образов. Затем выполнены аппаратная ECC-проверка,
запись и побайтный readback каждого этапа. **Финальный вариант установлен и
проверен владельцем:** «Да, работает всё что было задумано».

Один SOS-down блокирует и гасит экран, следующий разблокирует и пробуждает.
Отпускание/удержание не вызывает краткой вспышки и не запускает аварийный SOS.
Навигация и контакты v0.2.0 сохранены. Финальная сборка:
`python3 tools/build_sos.py --no-flash`; user SHA-256
`41aba70fd84346095a756ccc97dcbb33b23dcca4c9dba686351622c93f1a7f34`.

Ниже — разбор кода и история трёх испытанных SOS-вариантов. Два ранних
варианта сохранены для воспроизведения цепочки переходов, а не как финальный релиз.

## Новый результат: найден штатный путь запуска SOS

Адреса MMI — виртуальные, база `0x88000000`. Это не физические NAND-адреса.

| Этап | Адрес / данные | Что подтверждено |
| --- | --- | --- |
| Перевод аппаратного кода | `0x881771c0` | После нормализации входного кода функция ищет его в байтовой таблице; затем применяет дополнительное отображение. |
| Таблица перевода | `0x883da8c2`, 105 байт | Элемент с индексом `0x64` равен `0x27`: входной код `0x27` возвращает логический `0x64`. Цифры и центр находятся в той же таблице. |
| Подготовка долгого нажатия | `0x886a2c74` | Сохраняет логический код в одном из трёх 12-байтовых слотов и запускает таймер с аргументом `0x5dc` (1500). Единицы времени выводятся из использования API, не измерены на телефоне. |
| Обработка таймера | `0x886a31f2` → `0x886a2f1c` | По ID таймера возвращает сохранённый код, затем вызывает `0x886a2a84(r0=0xfc00, r1=код)`. Для кода `0x64` это событие `0xfc64`. |
| Общий маршрут | `0x886a2a84` | После фильтров посылает `класс+код` в оконный диспетчер `0x880a0a00`. Если окно не обработало событие, выполняется штатный default-путь через `0x88176caa` и `0x88176e1a`. |
| Выбор SOS | `0x88176e52` → `0x88176f42` | Сравнение `r0-0xfb20 == 0x144` выбирает именно `0xfc64`. |
| Проверка настройки SOS | `0x881c219e` | Читает настройку через NV API `0x881ed718`; при ошибке чтения записывает значение по умолчанию `1` через `0x881ed7fc`. Поэтому сама функция не является read-only диагностическим API для живого телефона. |
| Открытие SOS | `0x88176f4c` → `0x881c281c` | При разрешённой настройке вызывает подготовку SOS `0x881c2748` и открытие окна через `0x8809d2f4`. Альтернативная ветка использует `0x8834ea36`. |

Это связь с исполняемым SOS-модулем, а не догадка по инженерной строке `SOS`.
Обычные `0xfa64` / `0xfb64` не выбирают эту ветку default-обработчика.
`0xfd64` тоже её не выбирает: у данной прошивки разные механизмы `FC` и `FD`.

**Статическая связка `0x27 → 0x64 → FC64 → SOS` подтверждена.** Работа
перехвата именно физической SOS-кнопки подтверждена владельцем после прошивки.
Отдельный инструментальный захват аппаратных событий не выполнялся.

## Дополнительная находка в kernel

По файловому смещению `0xacc554` найдена 64-элементная таблица `uint16_t`,
похожая на аппаратную матрицу: содержит цифры `0x30..0x39`, центр `0x0d`,
неиспользуемые `0xffff`, а также `0x27` в элементе 36 (нумерация с нуля).

Kernel-getter по файловому смещению `0x1753b8` возвращает размер `0x40` и
указатель `0x81492354`. Найдена согласованная база загрузки `0x809c5e00`:

- ARM-вектор по смещению `0x200` соответствует `0x809c6000`; его указатель
  `0x809c623c` ведёт в реальный стартовый код по смещению `0x43c`.
- Вызовы из этого стартового кода в `0x80b7ee84` и `0x80bc2f50` при той же
  базе ведут в согласованные Thumb-функции.
- `0x809c5e00 + 0xacc554 == 0x81492354`: getter возвращает адрес именно
  найденной матрицы при таком непрерывном отображении.

Это усиливает связь kernel-матрицы с MMI-таблицей. Копирование/перемещение
секций при загрузке полностью не прослежено; расположение задней кнопки в
физической матрице и её реальные события ещё не захвачены.

## Что выяснилось про блокировку

Нужно различать три состояния:

- `0x81704114 + 3`: байт отложенного запроса блокировки;
- `0x81704114 + 0x24`: режим, который читает `0x881763e8`; функция возвращает
  `1` для значений 0/1 и `0` для остальных;
- `0x881af488`: предикат оконной блокировки, проверяющий окно `0x52` и его
  внутренний режим через `0x881aed44`. Это не чтение байта запроса.

`0x88176f7c(bool)` записывает байт запроса, проверяет контекст при включении и
вызывает `0x881763fe`; при выключении отменяет таймер `0x0a` через
`0x8871644e`. `0x881763fe` использует настройку времени автоблокировки из
`0x881e79ce` и планирует таймер. Значит, переключение этого байта **не доказано
как немедленный lock/unlock уже открытого экрана**.

### Немедленное создание и закрытие окна

Найден конкретный путь обычной блокировки:

1. `0x881aedbe()` проверяет окно `0x90098` и предикаты `0x881c59cc` /
   `0x880be5fa`. При двух последних препятствиях возвращает `0`.
2. Для обычного lock-окна (включая уже существующее) устанавливает режим
   `*(uint32_t *)(0x81708030 + 8) = 0`; вызывает `0x881e74c4(1)`.
3. Если окно `0x52` существует, вызывает `0x8809e4de(0x52)`; иначе открывает
   его через `0x8809d2f4(0x887a6eec, 0)` между парой вызовов
   `0x881878d4(1)` / `0x881878d4(0)`. В последнем случае также вызывает
   подготовку `0x881aed72()`.
4. Функция возвращает `1` и в некоторых ветках без нового открытия; результат
   нельзя считать самостоятельным доказательством фактической блокировки.

Таблица окна `0x887a6eec` содержит ID `0x52`. Его обработчик
`0x881af02c` зарегистрирован указателем по файловому смещению `0x1344b4`.

`0x881aee4a()` — штатная операция закрытия: проверяет наличие окна `0x52`
через `0x8809df7e`, затем вызывает **менеджер** `0x8834d13a(0x52)`.
Возвращает `1` также при отсутствии окна. Нельзя заменять это прямой записью
байта состояния или удалением callback.

Связка разрушения окна прослежена:

- `0x8834d13a` передаёт `0x8809d777` как destructor в `0x881794e6`.
- `0x8809d776` перед удалением посылает событие `0xf022` через
  `0x880a0744` при установленном флаге окна `+0x1e`.
- Обработчик lock-окна `0x881af02c(..., 0xf022, ...)` вызывает
  `0x881aeed2` и `0x881aeeb8`: отменяет таймеры, записанные в первых двух
  байтах структуры `0x81708030`, обнуляет эти байты.
- В обычных режимах вызывает `0x881766bc`, `0x881763fe`, затем
  `0x881aed54(2)` и подготовку `0x881aed72`. Специальный режим `3`
  сохраняется: setter `0x881aed54` не изменяет его.

Следовательно, штатное закрытие включает cleanup, а не только скрытие UI.
Это проверка кода отдельных этапов; весь оконный менеджер и runtime-окружение
не эмулированы целиком.

`0x881aee3c(arg)` — **другой** путь: режим `3` и открытие той же таблицы с
аргументом `arg`. Найден его вызывающий код `0x886d0eb6`, связанный с выбором
значения из списка. Его нельзя путать с обычной блокировкой.
`0x8817707a` меняет режим подсветки/ввода и в одной ветке сам создаёт lock-окно;
это не подходящая доказанная операция разблокировки.

### Важное уточнение фильтров

Раннее предположение, что `0x88177f5e` безусловно поглощает все неизвестные
клавиши при блокировке, было слишком грубым. Для кода `0x64` эта функция
возвращает `0` в проверенных комбинациях режимов и классов FA/FB/FC/FD;
при этом может вызывать обслуживающие функции таймеров.

Далее `0x88177eee` возвращает `1` при режиме 0/1 и активном предикате
`0x881af488`, в том числе для `FC00/0x64`. Иначе результат зависит от класса,
режима и сохранённого байта `+2`. Поэтому перехват только ветки
`0x88176f42` не обеспечивает переключение из обоих состояний. Нужно доказать
подходящий вход до этой фильтрации и корректный выход из lock-окна.

Возврат отдельного фильтра не равен результату всего диспетчера.
`0x881768e6` возвращает разрешение оконной передачи;
`0x886a2a84` вызывает `0x880a0a00` **только при ненулевом результате**.
В расширенной проверке при контролируемых внешних ответах:

- режим 0/1, предикат lock=true: передаются FA/FB/FC/FD/FE для кода `0x64`;
- режим 0/1, lock=false: передаётся FA; остальные зависят от сохранённого
  байта допуска `+2` (в этой проверке он принудительно нулевой);
- режим 2, сохранённый допуск нулевой: оконной передачи нет.

Callback lock-окна для `FA64/FB64/FC64/FD64/FE64` сам возвращает `0`, не
вызывая SOS. Будет ли затем default-путь, определяется вызывающим кодом;
нельзя называть этот возврат «событие поглощено» без контекста.

## Реализованная точка перехвата и последовательность кнопки

Все четыре разобранных маршрута входят в `0x886a2a84(r0=класс, r1=код)`:

- `0x886a2d98`: FA после аппаратного нажатия;
- `0x886a2ee6`: FB для обычного отпускания либо FD после долгого удержания;
- `0x886a2f48`: FC из таймера удержания;
- `0x886a2fb8`: FE из таймера повтора.

Вход расположен **до** оконных фильтров. Перехват только default SOS-ветки
менял бы долгое удержание и зависел от активного окна.

Реализованная логика кандидата: только для logical `0x64` переключать обычное
lock-окно на FA, подавлять FC/FE и оба варианта отпускания FB/FD. Для остальных
клавиш передавать события исходному обработчику. Штатная регистрация
`0x886a2c74` отвергает повторный hardware-down до FA-диспетчера, пока слот
этой клавиши занят. Слот очищается до передачи FB/FD. Дополнительный неизвестный
RAM-байт не используется. Эта гарантия относится к аппаратному маршруту;
произвольные прямые вызовы общего входа не считаются физическими нажатиями.

Штатные таймеры слота должны сохранять возможность cleanup. Функция
`0x886a2bda(код, out_long)` на отпускании отменяет таймеры повторов/удержания,
возвращает флаг long и очищает слот. Эмуляция всех трёх слотов с short/long
подтвердила этот путь. Подавление high-level FC само по себе не отменяет
таймер и не заменяет обработку отпускания.

Первые восемь байт входа `0x886a2a84` —
`f0 b5 8d b0 0c 46 28 21`: push, выделение стека, копирование аргумента,
установка размера. Здесь нет PC-relative инструкций, поэтому можно исследовать
trampoline с воспроизведением этих инструкций и возвратом к `0x886a2a8c`.
Trampoline реализован в `tools/sos.s`, отдельный сборщик — `tools/build_sos.py`.
Вход аппаратного сообщения вызывается из очереди MMI (`0x880a0888` →
`0x880a09aa` → `0x886a2d08`), той же цепочки, где штатный default открывает SOS.
При разблокировке кандидат повторяет переход режима в `2` через `0x881aed54`,
возобновление приостановленных служб `0x881aeeec`, затем managed-close
`0x881aee4a`. Preview-окно режима `3` существующим нажатием не закрывается.
В первом варианте перед обработкой всех пяти классов SOS вызывался штатный
`0x881768e6`; его разрешение оконной передачи игнорировалось, сами SOS-события
в окна не передавались. Финальный вариант пропускает этот wake-capable service
на FB/FC/FD/FE при существующей обычной блокировке; FA сохраняет его и переключает
состояние. Так устранена вспышка без изменения upstream cleanup слота/таймеров.

## Воспроизводимая проверка

`tools/check_sos_research.py` исполняет **штатный машинный код** в Unicorn:

```bash
python3 tools/check_sos_research.py
```

Требуются локальный исходный user-образ и `unicorn`. Проверка привязана к его
контрольной сумме; никаких бинарных дампов в документе или исходниках нет.

Проверено 447 случаев:

- все 256 входных кодов функции перевода;
- выбор SOS-ветки и альтернативы при выключенной настройке;
- поиск таймера и фактическая передача `FC00/0x64` в общий диспетчер;
- оба фильтра при контролируемых состояниях блокировки/режима/байта `+2`;
- конструктор lock-окна, его guard-ветки и штатная обёртка закрытия;
- реальный lock-предикат при наличии/отсутствии окна и четырёх режимах;
- cleanup события `0xf022` в обычных и специальном режимах;
- short/long cleanup всех трёх клавиатурных слотов;
- полный общий вход до оконной передачи для 30 комбинаций режима/lock/класса.
- аппаратный down/duplicate/hold/release всех трёх слотов, short и long.

NV API, логирование и внешние предикаты подменены контролируемыми ответами;
проверка останавливается перед открытием окна. Она доказывает разобранные
ветки, но не аппаратные события, полный UI или пригодность нового toggle.

## Первый SOS-вариант и пакет перехода

`experimental/sos/l728-user-sos-CANDIDATE.bin` — отдельный образ поверх v0.2.0.
SHA-256: `61edf9a3a9206d8f59baac6b4e3f7b55e5ab1d1f9cd88746777bfe2f15416681`.
Полезная нагрузка 168 байт, помещается в существующей последней странице.
Дельта: блок `0x17c`, страница 2 (код), `0x172`, страница 5 (перехват),
`0x13d`, страница 0 (размер). Порядок записи именно такой; откат к v0.2.0.

`tools/check_sos.py` прошёл 5684 случая: detour/trampoline, все 256 logical-кодов,
сохранение регистров/стека при порче volatile-регистров внешними функциями,
guards обычной блокировки, preview, реальный аппаратный lifecycle, полный
штатный input-service с внешними подменами, allowlist SRAM-helper для 1024 блоков.

Восстановлен BCH encoder GF(2^14), t=12, 168 parity bits на 1024 байта.
`tools/l728_ecc.py` использует reciprocal generator и порядок little-endian
main/big-endian parity. `tools/check_l728_ecc.py` проверяет 10880 секторов
сохранённых блоков и случайных NAND-регионов; все 6 свежих аппаратно
закодированных секторов последнего обновления совпали точно. В старом OOB
сохранены отдельные parity-bit ошибки: их аппаратный decoder не переписывал.
Неизменённые страницы и эти байты копируются без «исправления» metadata.
Software encoder не является decoder; перед записью требуется аппаратный decode.

`tools/sos_transition.py --prepare` уже создал отдельные ECC-блоки и точный
откат в `experimental/sos/transition`. `--check-plan` проверяет их хеши,
main/OOB и границы без USB. `--validate-device` читает семь текущих блоков,
сравнивает новый ECC с BootROM encoder, проверяет исправление внедрённых ошибок
в RAM и decode полных блоков. Только после него доступен явный `--apply`.
Отдельный SRAM-helper разрешает запись только `0x13d/0x172/0x17c`;
исходный релизный helper по-прежнему имеет прежний allowlist.

`tools/check_sos_transition.py` проверяет реальные операции пакета с подменённым
FDL: отказ без аппаратной валидации, mismatch текущих блоков, отказ ECC перед
первым erase, порядок записи, повторный apply без новых записей, возврат после
повреждения разрешённого блока и продолжение прерванного обновления.

## Аппаратная проверка пакета выполнена

После запуска владельцем `start_sos_validation.py` получена рабочая FDL-сессия
с BootROM `SPRD3` и chip ID `0x98180001`. Проверены семь текущих блоков:
`0x13d/0x143/0x145/0x14c/0x172/0x17a/0x17c`; каждый точно совпал с сохранённым
состоянием v0.2.0, включая main и OOB.

Для трёх целевых блоков аппаратный BootROM encoder воспроизвёл software ECC
точно; decoder исправил внедрённые ошибки в обоих секторах и проверил полные
64-страничные блоки. Журнал:
`experimental/sos/transition/validate-device-1791794221786191278.json`.
Дополнительный `--verify` из сессии агента также прошёл без NAND-записи.
Теперь план содержит `hardware_validated=true`.

На этом этапе образ и ECC-пакет были подготовлены к испытательной прошивке
с откатом к v0.2.0. RAM-валидация сама по себе не проверяла новый UI;
последующая запись и проверка владельцем описаны ниже.

## Процедура аппаратной проверки перед записью

Для первого SOS-перехода свежий readback и аппаратная проверка ECC без
NAND-записи запускались командой ниже. Для screen и финального исправления
использовались соответствующие флаги. Проверка UI выполнялась владельцем
после каждой установки, отдельно от RAM-валидации.

```bash
sudo python3 "/home/lain/Documents/Взлом трубы/tools/start_sos_validation.py"
```

Команда начинает с ранее успешного `spd_dump ... fdl /tmp/opencode/t117_fdl1.bin
0x6200 read_mem 0xffff0000 0x8000 ...`; телефон без батареи подключается с UP
после запуска ожидания. Никаких opcode erase/program на этом этапе нет.
Аппаратная валидация пакета завершена.

## Дополнение: гашение и пробуждение экрана

По запросу владельца подготовлен отдельный вариант `experimental/sos-screen/`.
SHA-256: `af9d36b31a0f160ad57aa60daa1ecbf80c5be8a07730cddf76ebbd28c6436046`.
Сборка: `tools/build_sos.py --screen`. Исходный установленный SOS-образ,
его ECC-план и rollback не перезаписывались.

Вариант сохраняет переключение обычной блокировки. После её фактического
открытия и обработки последующих SOS release/hold/repeat вызывает штатный
`MMIDEFAULT_CloseAllLight` (`0x8817707a(0)`). Он отменяет таймер подсветки,
выключает свет через `0x881ee570(0)` и переводит MMI-состояние `+0x24` в `2`;
`0x8817660c(1)` передаёт основной LCD в sleep через `0x881ede98(0,1)`.
Аргумент `0` в CloseAllLight исключает его ветку нового открытия lock-окна.
Если обычной блокировки нет, создание отклонено guard или открыт preview
режима `3`, экран этим hook не гасится.

При разблокировке после managed-close вызывается штатный
`0x88176886` — MMI wake/backlight service. `0x881766bc` выводит LCD из
состояния `2`, через `0x8817660c(0)` передаёт sleep=false, а последующие
ветки управления включают подсветку и восстанавливают её таймер.

По просьбе владельца выполнена одна целевая проверка собранного кода:
`tools/check_sos_screen.py`. Последовательность lock → hold/release →
unlock/wake прошла; release не оставляет экран включённым после блокировки.
Также в этой же проверке guard и preview не гасят экран. Аппаратные LCD/
power вызовы моделируются; штатные lock/CloseAllLight/wake wrapper инструкции
исполнялись. Последующее испытание владельцем обнаружило вспышку на release.

Переход с работающего SOS `61edf9...` меняет только блоки `0x17c` (код),
`0x13d` (размер). `tools/sos_screen_transition.py --prepare` подготовил ECC
и точный rollback к первому SOS; `--check-plan` прошёл. До аппаратной проверки
пакет имел `hardware_validated=false`. Проверка без NAND-записи:

```bash
sudo python3 "/home/lain/Documents/Взлом трубы/tools/start_sos_validation.py" --screen
```

Этот этап использует ранее успешную FDL-команду, затем свежий readback и
аппаратные encoder/decode в RAM. Проверка выполнена владельцем: все семь
текущих блоков совпали с установленным SOS, ECC двух целевых блоков проверен
аппаратным encoder/decoder, включая исправление ошибок в RAM.
Журнал: `experimental/sos-screen/transition/validate-device-1791795469462733648.json`.
Новый screen-план содержит `hardware_validated=true`.

После разрешения «ПРошивай» выполнена запись двух блоков `0x17c`, `0x13d`.
Оба readback совпали с целевыми SHA-256; итоговое чтение семи блоков прошло.
Журнал: `experimental/sos-screen/transition/apply-1791795581240656533.json`.
На этом этапе был установлен образ
`af9d36b31a0f160ad57aa60daa1ecbf80c5be8a07730cddf76ebbd28c6436046`;
владелец подтвердил выключение/включение, но заметил краткую вспышку.

## Устранение вспышки после блокировки

Владелец подтвердил работу screen-варианта, но заметил краткую вспышку:
штатный input-service на SOS release пробуждал экран перед повторным гашением.
По его просьбе подготовлен `experimental/sos-no-flash/`, образ SHA-256
`41aba70fd84346095a756ccc97dcbb33b23dcca4c9dba686351622c93f1a7f34`.

Дополнение `SOS_NO_FLASH` пропускает wake-capable service для FB/FC/FD/FE
только при существующей обычной блокировке. На FA service выполняется как
раньше, поэтому следующее нажатие пробуждает и разблокирует. При отсутствии
lock или preview режима 3 service сохраняется. Штатный аппаратный caller
уже очистил слот и таймеры до передачи FB/FD; его код не меняется.

Выполнена одна целевая проверка `check_sos_screen.py --no-flash`: между lock
и unlock ни один hold/release не вызвал даже краткого input-wake; unlock
и последующий release работают, guard/preview сохранены. Граница питания
моделируется; результат этой проверки отделён от последующего испытания владельцем.
Два ECC-блока и точный rollback к работающему screen-варианту подготовлены
`sos_no_flash_transition.py --prepare`; `--check-plan` прошёл.
Для аппаратной проверки перед установкой:

```bash
sudo python3 "/home/lain/Documents/Взлом трубы/tools/start_sos_validation.py" --no-flash
```

Аппаратная проверка завершена: `validate-device-1791796090691892903.json`.
По разрешению «Готово, можешь шить» записаны два блока и проверены все семь
итоговых readback. Журнал:
`experimental/sos-no-flash/transition/apply-1791796124144032981.json`.
В NAND установлен финальный no-flash-образ `41aba70f...`.
После нового запуска владелец подтвердил: «Да, работает всё что было задумано».
Это итоговая v0.3.0: SOS lock/unlock, гашение/пробуждение и отсутствие вспышки,
с сохранением клавиш и контактов v0.2.0. Проверка относится к одному аппарату
указанной версии, а не к произвольным UMS9117.
