# Philips Xenium L728: навигация 2/4/6/8

Исследовательский проект по добавлению управления меню и списками цифровыми
клавишами на Philips Xenium L728 (UMS9117). На проверенном телефоне патч
работает: `2/4/6/8` перемещают курсор как стрелки, включая список контактов.
Обычный набор номера и ввод текста сохранены.

**Изменение прошивки делается на свой риск.** Инструменты записи адресованы
конкретной плате/разметке L728 и не являются универсальными для UMS9117.
Перед любыми изменениями необходим полный проверенный дамп именно своего
аппарата и понимание процедуры возврата в BootROM/FDL.

## Аппаратная информация

- Модель: Xenium L728, аппаратная платформа UMS9117 / `ums9117_barphone`.
- USB BootROM: VID:PID `1782:4d00`; штатный USB-накопитель: `1782:4d01`.
- BootROM сообщает `SPRD3`; FDL сообщает Chip ID `0x98180001`.
- ОС/прошивка: RTOS, проект `ums9107_ST227_ZWX_L728_T107_RU`.
- Проверенная версия: `L728_T107_2628_V11A_RU_UMS9117_V1.0.10_Release_20260707_1725`.
- NAND: 128 MiB, 65536 страниц, 2048 байт данных + 64 байта OOB,
  64 страницы/блок. ID NAND — `B0 15`; он совпал с таблицами драйвера
  в kernel. Host ECC: два сектора по 1024 байта, 21 ECC-байт на сектор.
- Boot0 начинается со страницы 0, boot1 — `0x80`, kernel — `0x3340`,
  пользовательский MMI — `0x4f40`.
- Клавиша UP входит в BootROM-загрузчик: при снятой батарее удерживать UP
  и подключить USB.

## Результат

Локально собранный патч меняет семь страниц пользовательского MMI и
исправляет DHTB-размер образа. Исследованы обработчики списков, главного
меню и окон контактов; преобразование выполняется локально в обработчиках,
а не глобальным переназначением клавиатуры. В контактах 2/4/6/8 переводят
фокус со строки поиска на список. Посторонние события передаются штатному
обработчику.

В тестировании на одном L728 телефон штатно загрузился и поведение совпало
с целью. Для точного воспроизведения используются `tools/navigation.s`,
`tools/build_navigation.py`, `tools/check_navigation.py` и приватный для
владельца исходный user-раздел. Для проверки исходников без телефона нужен
Python с `capstone`, `pyelftools`, `unicorn`, а также clang/LLD и objcopy.

## Воспроизведение анализа и патча

1. Сделайте **полный ECC-корректированный дамп своего телефона**, включая
   OOB, и сохраните его офлайн. Не публикуйте свой NAND-дамп: в разделах
   могут быть контакты, пользовательские файлы, NV, калибровки и
   идентификаторы устройства.
2. Извлеките пользовательский образ из FTL. В этой версии его логическое
   содержимое начинается с физической страницы `0x4f40`; реальное отображение
   блоков/FTL обязательно проверьте на собственном дампе.
3. Поместите ECC-корректированный образ в `backup/l728-user-ecc.bin`.
   Сборщик проверяет SHA-256 и исходные callback-указатели; это намеренно
   не позволит применить патч к неизвестной версии.
4. Выполните `python3 tools/build_navigation.py`. Выходные файлы создаются
   в `experimental/` (этот каталог игнорируется Git). Проверьте отчёт и
   SHA-256 образа перед дальнейшей работой.
5. `python3 tools/check_navigation.py` исполняет обёртки в Unicorn и проверяет
   регистры, стек, отображение событий и границы патча. Это офлайн-тест, не
   заменяющий проверку модели/версии и физического NAND.

Для анализа кода `tools/inspect_user.py IMAGE ADDRESS` показывает Thumb-
дизассемблирование; `--arm` переключает на ARM, `--refs` ищет указатель.
Адреса UI относятся к виртуальной базе user-раздела `0x88000000`, который
подгружается страницами из FTL; это не прямой алиас `0x82000000`.

## NAND и восстановление

В репозитории намеренно **нет полного NAND, пользовательского раздела,
персональных блоков/OOB, NV или конфигурации телефона**. Владелец устройства
должен подготовить оригинальные блоки для своего дампа и хранить резервную
копию локально. `tools/l728-reader.c` — чтение; `tools/l728-correct.c` —
аппаратная ECC-коррекция в RAM; `tools/l728-encode.c` — генерация host ECC
в RAM. Диагностические помощники и блоковые операции находятся в
`tools/l728-diagnostic.c`, `tools/l728-cache-test.c`, `tools/l728-block-io.c`.

Для исследованной версии менялись физические блоки `0x13d`, `0x143`, `0x145`,
`0x14c`, `0x17a`, `0x17c`; структура каждого блока — 64 страницы по 2112 байт.
Порядок записи: добавленный код, таблицы callback, заголовок образа последним.
Полный подготовленный план/образы блоков из тестового телефона не включены.
Скрипты `prepare_navigation_blocks.py` и `navigation_blocks.py` пока
содержат абсолютные пути `/tmp/opencode` и ожидают точные локальные файлы
резервной копии/FDL-помощников из исследовательской сессии. Их следует
  адаптировать и независимо проверить на собственной копии перед применением.
  Запись требует `--apply --confirm-destructive-write`; восстановление —
  `--restore --confirm-destructive-write`.

## Что не опубликовано и почему

- Полные образы kernel/user и полный NAND: возможны личные данные, NV,
  калибровки и аппаратные идентификаторы; кроме того, это проприетарная
  прошивка производителя.
- Локальный `tfboot.bin`: его SHA-256 отличается от извлечённого из ECC-
  исправленного kernel файла на 28 байтах; происхождение этой копии не
  подтверждено, поэтому она не используется как исходный артефакт.
- Дампы FDL/экспериментальные блоки конкретного телефона: сохраняйте офлайн.

В дампах, прошедших проверку, не обнаружено фактического IMEI/серийного
номера. Найденные строки `IMEI` и форматы `%IMEI` — код/сообщения прошивки,
не номер аппарата. Это не гарантия, что произвольная копия `tfboot.bin` или
NAND другого устройства безопасна для публикации.
